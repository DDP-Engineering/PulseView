## Design

Components: `02_Tools/build/build_windows_mxe.sh` (the `build_libsigrokdecode`
and staging steps), `02_Tools/build/images/Dockerfile.mingw` (the
`/opt/sigrok-deps` bake in the `final` stage), `02_Tools/upstream/upstreams.lock.toml`,
and one new file `02_Tools/test/windows_python_smoke.sh`.

Two artifacts, both from www.python.org over HTTPS, both pinned in the lock as
`[[artifact]]` with sha256 and baked into the image [REQ-PLAT-537f1db4]:
`python-3.13.15-embed-amd64.zip` (`d1f04d99..a2cf`) is the runtime, and
`Python-3.13.15.tar.xz` (`1e66a794..4a76`) is the header source. `fetch_verified`
keeps its shape - image copy first, network only as a fallback for an older
image - so `--offline` still passes. `PY_BASE` becomes the HTTPS release
directory; the three `PY_SHA_*` constants are replaced by two.

Headers are `Include/**` from the tarball plus `PC/pyconfig.h.in` copied to
`Include/pyconfig.h` [REQ-PLAT-84979f05]. `pyconfig.patch` is dropped, not
carried: 3.13's own header already contains the `__MINGW32__` block that
defines `MS_WIN64`, which was the patch's whole content.

Interface: the script gains `PY_VER=3.13.15` and `PY_TAG=313` as the only
version-bearing values, and the unpacked tree moves from `${PREFIX}/Python34`
to `${PREFIX}/python-win/{include,libs}` so a future bump is two lines.
`python3.pc` keeps its name and gains `Version: 3.13`; libsigrokdecode's
`configure.ac` probes named modules (`python-3.12-embed` and friends) and then
falls back to `python3 >= 3.2`, which is the alternative our file satisfies, so
that version list still does not need extending. `gendef`/`dlltool` on
`python313.dll` is unchanged and yields `libpython313.a` from 1664 exports.

Staged layout [REQ-PLAT-84979f05]: executables at the top, the embeddable
package's contents beside them, decoders under `share/libsigrokdecode/`. The
package's own `python313._pth` sits next to `python313.dll` and fixes
`sys.path` to `[python313.zip, .]`, which is what puts the stdlib and the loose
`.pyd` files - `_ctypes.pyd` among them, for upstream bug #1409 - on the path
without any `PYTHONPATH` or registry involvement.

Test seams. REQ-PLAT-84979f05 attaches at `02_Tools/test/windows_python_smoke.sh`,
run on the Windows host against `07_Delivery/staging/`, which adds an f-string
decoder, lists, removes it and lists again. Two cheap in-build guards back it:
a compile-only probe with `_Static_assert` on `sizeof(Py_ssize_t) == 8`,
`PY_VERSION_HEX >= 0x030900F0` and `MS_WIN64`, sited in `build_libsigrokdecode`;
and an import-closure walk at staging time that fails if any PE in the tree
imports a non-`api-ms-win-*` DLL the tree does not contain.
REQ-PLAT-537f1db4 attaches at `build_windows_mxe.sh --offline --clean`.

Rejected: taking headers from the `python.3.13.15` nuget package. It ships a
ready `include/pyconfig.h`, but that file is byte-identical to the tarball's
`PC/pyconfig.h.in` modulo line endings, so it buys nothing and adds a second
host to the trust set. Also rejected: hand-picking `.pyd` files to keep the
tree near its current size. The import-table walk shows the package is already
self-closed - `_ctypes` needs `libffi-8.dll`, `_hashlib` needs `libcrypto-3.dll`
- and a missing module surfaces as a decoder that silently fails to load, which
is the exact failure this task exists to remove.
